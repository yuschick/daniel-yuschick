# DY Design System — Accessibility Rules

> **Core Philosophy:** Clear and stable code over complex abstractions.

Rule IDs are permanent: rules may be reordered or retired, but an ID is never reused. When guidance overlaps, the more specific rule wins and the paired ✅/❌ examples are authoritative. `A11Y-*` rules take precedence over any conflicting rule. See the [standards index](README.md) for every domain.

## Accessibility Rules

Accessibility is a release-blocking requirement, not an enhancement. Every component **MUST** meet **WCAG 2.2 Level AA**. Where an `A11Y-*` rule conflicts with any other rule, the `A11Y-*` rule wins.

### A11Y-01 · WCAG 2.2 AA Conformance (Non-Negotiable)

- Every component, state, and pattern **MUST** conform to all WCAG 2.2 Level A and Level AA success criteria. A component with a known A or AA violation **MUST NOT** be merged.
- The following WCAG 2.2 AA criteria are explicitly enforced by the rules below and **MUST** be satisfied: 1.1.1 Non-text Content, 1.3.1 Info & Relationships, 1.4.1 Use of Color, 1.4.3 Contrast (Minimum), 1.4.4 Resize Text, 1.4.10 Reflow, 1.4.11 Non-text Contrast, 1.4.12 Text Spacing, 1.4.13 Content on Hover or Focus, 2.1.1 Keyboard, 2.1.2 No Keyboard Trap, 2.4.3 Focus Order, 2.4.7 Focus Visible, 2.4.11 Focus Not Obscured (Minimum), 2.5.3 Label in Name, 2.5.7 Dragging Movements, 2.5.8 Target Size (Minimum), 3.3.1 Error Identification, 3.3.2 Labels or Instructions, 3.3.3 Error Suggestion, 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication (Minimum), 4.1.2 Name/Role/Value, 4.1.3 Status Messages.
- Any custom widget **MUST** implement the keyboard and ARIA contract of the matching **WAI-ARIA Authoring Practices (APG)** pattern. Inventing bespoke interaction models for solved patterns is **STRICTLY FORBIDDEN**.

### A11Y-02 · Rule of Least Power (HTML → CSS → JS)

- Every feature **MUST** be built with the least powerful technology that achieves it semantically: **native HTML first, then CSS, and only then JavaScript.**
- JavaScript **MUST NOT** re-implement behavior the platform already provides. Escalating to JS is permitted only when HTML and CSS — while still satisfying every other rule here — cannot meet the requirement, and the reason **MUST** be justifiable.

| Need                      | Use first (HTML / CSS)                         | Forbidden when a native equivalent works  |
| :------------------------ | :--------------------------------------------- | :---------------------------------------- |
| Disclosure / accordion    | `<details>` / `<summary>`                      | JS toggle on `<div>`s                     |
| Modal dialog              | `<dialog>` + `.showModal()`                    | `<div role="dialog">` + JS focus trap     |
| Transient popover / menu  | `popover` attribute + anchor positioning       | JS show/hide + outside-click listeners    |
| Conditional layout        | Container queries, `:has()`                    | `ResizeObserver` / `matchMedia` branching |
| Form validation messaging | Native constraint validation + `:user-invalid` | JS-only validation gating                 |
| Sticky / positioned UI    | `position: sticky`, CSS anchor positioning     | JS scroll listeners                       |

### A11Y-03 · Native Semantic HTML First

- Components **MUST** render the native element that already carries the correct role, state, and keyboard behavior instead of applying ARIA to a generic `<div>`/`<span>`. **No ARIA is better than bad ARIA.**
- Mandated element choices: actions → `<button>`; navigation targets → `<a href>`; disclosure/accordion → `<details>`/`<summary>`; dialogs → `<dialog>`; navigation regions → `<nav>`; lists → `<ul>`/`<ol>`/`<li>`; headings → `<h1>`–`<h6>`; form controls → `<input>`/`<select>`/`<textarea>` with `<label>`; tabular data → `<table>`.
- A `<div>` or `<span>` **MUST NOT** be given an interactive role (`role="button"`, `role="checkbox"`, `role="link"`, etc.) when a native element exists. Custom-role widgets are permitted **only** for patterns with no native element (e.g., tabs, combobox, tree) and then **MUST** fully implement the APG keyboard spec (A11Y-06).
- ARIA **MUST NOT** duplicate or contradict native semantics (e.g., `role="button"` on a `<button>`, or `aria-disabled` alongside native `disabled`).

```tsx
/* ✅ Correct: native disclosure — keyboard, focus, and state for free */
export const Accordion = function Accordion({
  ref: externalRef,
  summary,
  children,
  ...htmlAttributes
}: AccordionProps) {
  const internalProps = { ref: externalRef, className: styles.accordion };
  return (
    <details {...mergeProps(internalProps, htmlAttributes)}>
      <summary>{summary}</summary>
      {children}
    </details>
  );
};

/* ❌ Incorrect: div soup re-implementing what <details>/<summary> already provide */
<div role="button" tabIndex={0} onClick={toggle} onKeyDown={handleKeyDown}>
  {summary}
</div>;
```

### A11Y-04 · Accessible Name & Role for Every Interactive Element

- Every interactive element **MUST** expose a non-empty accessible name (visible text, an associated `<label>`, `aria-label`, or `aria-labelledby`).
- Icon-only controls **MUST** require an `aria-label` (or visually hidden text). The design system **MUST** enforce this at the type level via a discriminated union — a consumer **MUST NOT** be able to render an icon-only control without a name.
- Where a control has visible text, its accessible name **MUST** contain that visible text (2.5.3 Label in Name).
- Decorative graphics **MUST** be hidden from assistive tech (`aria-hidden="true"` or empty `alt=""`); meaningful graphics **MUST** provide a text alternative (1.1.1).

```tsx
/* ✅ Correct: icon-only variant makes the accessible name mandatory at compile time */
interface LabeledIconButtonProps {
  children: React.ReactNode; // visible text supplies the name
  'aria-label'?: string;
}
interface IconOnlyButtonProps {
  children?: never;
  'aria-label': string; // ❗ required when there is no visible text
}
export type IconButtonProps = LabeledIconButtonProps | IconOnlyButtonProps;
```

### A11Y-05 · Disabled & Pending Buttons Use `aria-disabled` (Never Native `disabled`)

- A `<button>` (or `role="button"` element) that is disabled or pending **MUST NOT** use the native `disabled` attribute. It **MUST** set `aria-disabled="true"` and neutralize activation in its own handlers so the control stays focusable and announced while non-operational.
- The element's `onClick` (and any `onKeyDown` activation) **MUST** early-return when the button is disabled or pending, before invoking the consumer's callback.
- Pending state **MUST** additionally set `aria-busy="true"` (and `data-pending="true"` for styling) so assistive tech announces the in-progress state.
- Disabled/pending **styling MUST** target `[aria-disabled="true"]` and/or `[data-pending="true"]` — never `[disabled]` (see CSS-06, CSS-07).
- The following comment **MUST** appear above every `<button>` implementation that applies this pattern:

```tsx
export const Button = function Button({
  ref: externalRef,
  isDisabled = false,
  isPending = false,
  onClick,
  children,
  ...htmlAttributes
}: ButtonProps) {
  /*
   ** The native HTML 'disabled' attribute is one of the rare cases where it does more harm than good.
   ** When using 'disabled' the element is not clickable, but it's also not focusable or readable by assistive technologies.
   ** Instead, we use aria-disabled and prevent click/press events manually.
   ** This way, disabled buttons can still be understood by assistive technologies while being non-operational.
   */
  const isInoperable = isDisabled || isPending;

  const handleClick = (event: React.MouseEvent<HTMLButtonElement>) => {
    if (isInoperable) {
      event.preventDefault();
      return;
    }
    onClick?.(event);
  };

  const internalProps = {
    ref: externalRef,
    type: 'button' as const,
    'aria-disabled': isInoperable ? 'true' : undefined,
    'aria-busy': isPending ? 'true' : undefined,
    'data-pending': isPending ? 'true' : undefined,
    onClick: handleClick,
  };

  return (
    <button {...mergeProps(internalProps, htmlAttributes)}>{children}</button>
  );
};

/* ❌ Incorrect: native `disabled` removes the button from the accessibility tree and focus order */
<button disabled={isDisabled}>{children}</button>;
```

### A11Y-06 · Full Keyboard Operability

- Every interactive element **MUST** be fully operable with the keyboard alone (2.1.1), in a focus order that matches visual order (2.4.3), with no keyboard traps (2.1.2).
- Native elements **MUST** be used to inherit keyboard behavior for free (A11Y-03). Custom widgets **MUST** implement the exact keys from their APG pattern (e.g., arrow keys, `Home`/`End`, `Enter`/`Space`, `Escape`, typeahead).
- `tabindex` **MUST** be only `0` (natural order) or `-1` (programmatic focus). **Positive `tabindex` values are STRICTLY FORBIDDEN.**
- Overlays (dialog, menu, popover) **MUST** close on `Escape` and **MUST** return focus to the triggering element on close. Modal dialogs **MUST** trap focus while open — `<dialog>.showModal()` provides this natively.
- Any action available by pointer **MUST** also be available by keyboard; drag-only interactions **MUST** provide a single-pointer and keyboard alternative (2.5.7).

### A11Y-07 · Visible, Unobscured Focus

- Every focusable element **MUST** have a visible focus indicator, and it **MUST NOT** be removed without an equally visible replacement (2.4.7). `outline: none` with no replacement is **STRICTLY FORBIDDEN**.
- Focus styling **MUST** use `:focus-visible`, render via `outline`/`border` (never `box-shadow`; see CSS-08), and meet ≥ 3:1 non-text contrast against adjacent colors (1.4.11).
- A focused element **MUST NOT** be fully hidden by sticky headers, toolbars, or overlays (2.4.11).

### A11Y-08 · Color, Contrast & Non-Color Cues

- Text and images of text **MUST** meet ≥ 4.5:1 contrast (≥ 3:1 for large text: ≥ 24px, or ≥ 18.66px bold) (1.4.3).
- UI component boundaries, focus/selection states, icons, and meaningful graphics **MUST** meet ≥ 3:1 against adjacent colors (1.4.11).
- Color **MUST NOT** be the sole means of conveying information, state, or error (1.4.1). Pair color with text, an icon, underline, or shape (e.g., an invalid field shows an icon and message, not only a red border).
- All color pairings **MUST** come from contrast-verified design tokens (no hardcoded colors; see CSS-07) and **MUST** hold their contrast in light, dark, and forced-colors modes (see CSS-08).

### A11Y-09 · Minimum Target Size

- Interactive targets **MUST** be at least `24×24` CSS px, or provide an equivalent ≥ 24px hit area via padding/spacing (2.5.8). Adjacent targets **MUST** be spaced so a 24px circle centered on one does not overlap another.
- The design-system default interactive size **SHOULD** target ≥ `44×44` px for comfortable touch ergonomics.

### A11Y-10 · Motion, Animation & Timing Safety

- Motion **MUST** respect `prefers-reduced-motion` (see CSS-03).
- Content **MUST NOT** flash more than three times per second (2.3.1).
- Any auto-updating, moving, scrolling, or auto-playing content lasting more than 5s **MUST** provide pause/stop/hide controls (2.2.2), and time limits **MUST** be avoidable or adjustable (2.2.1).
- Auto-dismissing messages (e.g., toasts) **MUST NOT** be the only delivery of important information and **MUST** remain reachable.

### A11Y-11 · Accessible Forms, Labels & Errors

- Every form control **MUST** have a programmatically associated `<label>` (or `aria-labelledby`). Placeholder text **MUST NOT** be the only label.
- Required, format, and constraint information **MUST** be conveyed as text (3.3.2), not by color or an asterisk alone.
- Validation errors **MUST** be identified in text, associated to the field via `aria-describedby`, and the field marked `aria-invalid="true"` (3.3.1); actionable correction guidance **MUST** be provided when known (3.3.3).
- Native constraint validation and CSS `:user-invalid`/`:invalid` **MUST** be preferred over JS validation (A11Y-02). Related controls (radios, checkboxes) **MUST** be grouped with `<fieldset>`/`<legend>`.
- Previously provided information **MUST NOT** be required to be re-entered in the same flow (3.3.7); paste and password managers **MUST NOT** be blocked, and no cognitive-function test may be the only authentication method (3.3.8).

### A11Y-12 · Status Messages & Live Regions

- Dynamic updates that do not move focus (validation summaries, toasts, async results, pending→done transitions) **MUST** be announced through an appropriate live region: `role="status"` / `aria-live="polite"` for non-urgent, `role="alert"` / `aria-live="assertive"` for urgent (4.1.3).
- The live-region container **MUST** exist in the DOM before its content changes; announcements **MUST NOT** rely on moving focus.

### A11Y-13 · Content Structure, Landmarks & Reflow

- Structure **MUST** be semantic: headings in a logical order, landmark elements (`<main>`, `<nav>`, `<header>`, `<footer>`, `<aside>`), and programmatic relationships preserved (1.3.1).
- Layouts **MUST** reflow without loss of content or function at 320 CSS px width / 400% zoom (1.4.10) and support 200% text zoom (1.4.4) — use logical properties and relative units (see CSS-10); fixed-`px` containers that clip content are **STRICTLY FORBIDDEN**.
- User text-spacing overrides **MUST NOT** break layout or clip content (1.4.12).
- Content revealed on hover or focus **MUST** be dismissable (via `Escape`), hoverable, and persistent (1.4.13).

### A11Y-14 · Accessibility Verification

- Every component **MUST** pass automated accessibility checks (`axe`, run as Storybook tests) with **zero violations** in CI (FS-05).
- Automated checks are necessary but not sufficient: each component **MUST** be manually verified for keyboard operability and screen-reader output before merge.

## Pre-Submission Checklist

- [ ] Meets WCAG 2.2 AA; custom widgets follow the matching WAI-ARIA APG pattern (A11Y-01)
- [ ] Built with the least powerful tech: HTML → CSS → JS (A11Y-02)
- [ ] Native semantic elements used instead of ARIA-on-`div` (A11Y-03)
- [ ] Every interactive element has an accessible name; icon-only requires `aria-label` at the type level (A11Y-04)
- [ ] Buttons use `aria-disabled` (never native `disabled`) with a click/press guard + the required comment; pending sets `aria-busy` (A11Y-05)
- [ ] Fully keyboard operable; no traps; `Escape` closes overlays; focus returns to trigger; no positive `tabindex` (A11Y-06)
- [ ] Visible `:focus-visible` indicator via `outline`/`border` ≥ 3:1, never removed (A11Y-07)
- [ ] Text ≥ 4.5:1, UI/graphics ≥ 3:1; color is never the sole cue (A11Y-08)
- [ ] Interactive targets ≥ 24×24 px with adequate spacing (A11Y-09)
- [ ] Respects reduced motion; ≤ 3 flashes/s; auto-motion is pausable (A11Y-10)
- [ ] Inputs have associated `<label>`; errors in text + `aria-describedby` + `aria-invalid` (A11Y-11)
- [ ] Status/async updates announced via a live region (A11Y-12)
- [ ] Correct headings/landmarks; reflows at 320px / 400%; hover/focus content dismissable (A11Y-13)
- [ ] Zero `axe` violations + manual keyboard & screen-reader check (A11Y-14)
